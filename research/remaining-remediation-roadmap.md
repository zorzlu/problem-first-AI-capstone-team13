## Immediate Non-Eval Fixes

Status: completed.

### 1. Add Frontend Env Typing

Current finding:

- `frontend/src/api/client.ts` uses `import.meta.env.VITE_API_BASE_URL`.
- `frontend/vite.config.ts` uses `VITE_API_PROXY_TARGET`.
- There is no `vite-env.d.ts` typing file for these custom env vars.

Fix:

- Add `frontend/src/vite-env.d.ts`.
- Type:
  - `VITE_API_BASE_URL`
  - `VITE_API_PROXY_TARGET`

Why:

- Current Vite docs recommend declaring custom `import.meta.env` variables for type safety and IDE support.

Status:

- Done via `frontend/src/vite-env.d.ts`.

### 2. Tighten Vite Env Loading

Current finding:

- `frontend/vite.config.ts` uses:

```ts
loadEnv(mode, process.cwd(), '')
```

- That loads all environment variables, not only Vite-prefixed variables.

Fix:

```ts
loadEnv(mode, process.cwd(), 'VITE_')
```

Why:

- The proxy target is already named `VITE_API_PROXY_TARGET`.
- Loading all env vars is broader than needed.
- Vite docs confirm `VITE_` is the client-exposed prefix and `loadEnv` defaults to `VITE_`.

Status:

- Done in `frontend/vite.config.ts`.

### 3. Python Dependency Lock Strategy

Original finding:

- `backend/requirements.txt` contained bounded ranges.
- `backend/requirements.lock` was generated from the local Windows venv using `pip freeze`.
- That lock could include platform-specific packages such as `pywin32` and did not provide a clean project-level dependency workflow.

Fix:

- Added `backend/pyproject.toml` with backend dependency ranges and Python version.
- Added `backend/uv.lock` generated by `uv lock`.
- Removed `backend/requirements.txt` and `backend/requirements.lock` to avoid dual ownership.
- Updated CI and VS Code tasks to use `uv sync --project backend --frozen`.
- Verified backend tests through a fresh temporary uv environment using the committed lock.

Status:

- Done. `backend/pyproject.toml` plus `backend/uv.lock` is now the backend dependency source of truth.

### 4. Make Python Dependency Ownership Explicit

Original finding:

- Root `pyproject.toml` declared:

```toml
dynamic = ["dependencies"]
```

- Actual backend dependencies lived in `backend/requirements.txt`.

Fix:

- Root `pyproject.toml` is now only a lightweight workspace/tool project.
- Backend dependency ownership moved to `backend/pyproject.toml`.
- `backend/pyproject.toml` uses `[tool.uv] package = false` because the backend is run as an app, not built as a distributable package.

Status:

- Done.

### 5. Document And Optionally Prewarm Local Embedding Model

Current finding:

- The local embedding model is selected in `backend/memory.py`:
  - `EMBEDDING_MODEL`, default `BAAI/bge-small-en-v1.5`
  - `EMBEDDING_CACHE_DIR`, default `backend/state/fastembed_cache`
- The model is lazily loaded through `fastembed.TextEmbedding`.
- First use may download the model into the cache directory.
- If loading fails, the code falls back to lexical similarity.

Fix:

- Document first-run behavior in README.
- Add an optional prewarm/check command:

```bash
python -c "from backend.memory import is_embedding_active; print(is_embedding_active())"
```

Better future fix:

- Add a small script under `backend/scripts/` such as `prewarm_embeddings.py`.
- It should print:
  - active model name
  - cache directory
  - whether neural embeddings are active or lexical fallback is active

Status:

- Done via `backend/scripts/prewarm_embeddings.py`.

### 6. Document Frontend Env Behavior

Current finding:

- `frontend/.env.example` exists.
- README should clearly explain the two frontend env variables.

Fix:

- Add README section:
  - Local dev normally uses relative `/api` plus Vite dev proxy.
  - `VITE_API_PROXY_TARGET` controls the dev proxy target.
  - `VITE_API_BASE_URL` is for deployed frontend/backend on different origins.

Status:

- Done in README.

### Backend: Graph Expansion And State Coordination

Current state:

- Multiple workers or distributed deployments need an external store/queue.

- Move background expansion to a queue/worker.

## Deferred Eval Strategy

Status:

- Deferred by request.
- Existing eval runner exists under `backend/evals/runner.py`.
- Eval execution is intentionally outside the analyst UI.

Future eval topics:

### 1. Eval Dataset Versioning

- Version eval sets and expected assertions.
- Make behavior changes explicit when memory/routing evolves.

### 2. Eval Isolation

Each eval run should isolate or reset:

- catalyst ledger
- graph expansion status
- graph state, when relevant
- embedding/vector state, when relevant
- runtime settings/model route configuration

### 3. Separate Eval Suites

Recommended suites:

- direct extraction quality
- duplicate/update memory behavior
- cross-impact routing correctness
- graph expansion quality
- synthesis grounding
- guardrail degradation behavior
- latency/cost/token usage by semantic LLM step

### 4. Phoenix / Arize Usage

Recommended direction:

- Do not add eval execution to the analyst UI.
- Run evals from terminal, CI, or operator workflow.
- Emit Phoenix-friendly spans and metadata.
- Make branch/run comparison easy.

### 5. Model-Route Change Evaluation

When changing provider/model routes:

- Compare pass/fail quality.
- Compare latency.
- Compare token/cost estimates.
- Compare memory side effects.
